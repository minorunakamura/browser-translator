# 文中の要素を本物の HTML タグ（idDup）で送る

## 目的

段落の文中の要素（`a`・`code`・`strong`・`em` など）を、番号付きタグ（`<a1>`・`<c1>`）ではなく本物の HTML タグで PLaMo に送り、タグが合わずに訳せない段落を減らす。あわせて、原文に `<h1>` のようなタグそっくりの文字列がある段落も訳せるようにする。

根拠（Probe、`.pi/verification-evidence/tag-format-probe-20261127/`。Git 管理外）:

- round1・round2: 基準ページと react.dev/learn 系 4 ページの 177 段落（文中の要素を含み、30 文字以上）を 0.8B / 2B（Q4_K_M、temperature 0）で比較。番号付きタグは 166/177（0.8B）・171/177（2B）、idDup は 176/177（両モデル）。番号付きタグの失敗はすべて idDup で成功した。idDup の失敗は両モデルとも同じ 1 段落（`<a><strong>Props</strong> are like arguments you pass</a> …`。入れ子で出力の形が崩れた）。
  - 入れ子を含む 60 段落: idDup 58/60、番号付き 59/60。
  - `& < >` をエンティティにして送った 13 段落: 両モデルとも全件、エンティティのまま返った。番号付きタグでは、このうち 3 段落が `unknown h1` で失敗していた。
  - 判定は `round2/scripts/recheck2.ts` の `check`（形が正しく、開始タグの数・種類・`id` が原文と対応）。開始タグ（名前 + 属性）の組が原文と完全に一致するかで判定し直しても、同じ 176/177 だった。
- round3（`round3/probe3.ts`・`res3.json`、12 段落の小さな例 × 2 モデル）: `sup`・`kbd`・`br`・`img`・`abbr`・`sub`・`mark`・`small`・`s`・`u`・`span`・カスタム要素 `my-badge` を実際の名前で送って 24/24。空の要素を `<br></br>` のように開始と終了の組で送っても保たれた。

## 要件・決定事項

正式な前提は `docs/designs/browser-translator.md`「抽出とタグ」と `docs/plans/browser-translator-initial.md`。このうち、タグの形式に関する次の記述を、この Plan が置き換える（ユーザーと合意済み、2026-11-27）。

- 置き換える記述: 「段落内の `a`、`code`、`strong`、`em` などを `<a1>`、`<c1>`、`<b1>` のような番号付きタグに置き換えて送る」「それ以外の要素も番号付きタグ（`x`）として包む」と、README「現在の制限」の「原文に `<h1>` のようなタグそっくりの文字列がある段落は訳さず、原文のまま ⚠ の目印を付ける」。
- 新しい方針:
  1. **タグの名前**: 要素の名前（`localName`）をそのまま使う。`a`・`code`・`strong`・`em` 以外（`span`・`sup`・`kbd`・`br`・`img`・カスタム要素など）も実際の名前で送る。変換表（`a`→`a`、`strong`→`b` など）と `x` は廃止する。
  2. **対応の付け方（idDup）**: 段落の中で同じ名前の要素が 2 つ以上あるときだけ、その名前の要素すべてに `id="<n>"` を付ける。`n` は段落内のすべての要素を文書順に数えた通し番号（1 から）。名前が段落内で 1 つだけの要素には属性を付けない。元の要素の属性（`href` など）は送らない。
  3. **入れ子**: 特別扱いせず、そのまま入れ子のタグで送る。
  4. **空の要素**（`br`・`img` など、中に文字がない要素）: いまと同じく子を送らず、`<br></br>` のように開始と終了の組で送る。復元ではいまと同じく元の要素を丸ごと複製する。
  5. **エスケープ**: 文字列部分の `&`・`<`・`>` を `&amp;`・`&lt;`・`&gt;` にして送る。訳文の文字列部分は、この 3 つだけを元の文字に戻す（他のエンティティは戻さない）。
  6. **検証**: 訳文のタグが、入れ子の形として正しく（開始と終了が対応し、交差しない）、開始タグ（名前 + 属性）の組が原文とちょうど一致すること。原文にない名前・属性のタグ、抜け、重複は不一致。対応は、名前が 1 つだけの要素は名前で、同じ名前が複数ある要素は `id` で付ける。訳文のタグの順序は原文と違ってよい。
  7. **`code` の中身**: いまと同じく、訳文の中身にかかわらず原文の中身を使う。
  8. **訳し直し**: いまと同じ。合わなければ 1 回だけ訳し直し（temperature 0.3）、それでも合わなければ原文のまま ⚠。番号付きタグなど別の形式での再送はしない。
- 直列モードの翻訳履歴は、送った文字列と返ってきた訳文をそのまま使う（形式が新しいタグになるだけ）。
- 用語集の照合は、タグを取り除き、3 つのエンティティを元の文字に戻した文字列で行う（いまの「タグは照合にも語の区切りにも影響しない」を維持）。

## 制約・対象外

- 対象外: 送り方（並列・直列）、`context`、用語集の仕組み、表示方法、段落の抽出規則、`MutationObserver` / SPA の扱い、`background.ts` の送信・訳し直しの温度。
- 対象外: Probe で失敗した入れ子の 1 段落を個別に救う工夫（外側だけ送る、別形式で再送するなど）。既存の訳し直し → ⚠ で扱う。
- 対象外: 8B での比較、訳文の品質の定量評価。
- 番号付きタグと新しい形式の両方を持たない（設定や切り替えは作らない）。
- 作業開始時点で `main` に未コミット変更はない（Issue #4 は PR #9 で main にマージ済み、ブランチ `feat/bilingual-dynamic` はローカルで削除済み）。Implementation は `main` から新しいブランチを作って行う。開始時に未コミット変更があれば保持し、変更・破棄しない。
- `docs/plans/browser-translator-initial.md` は過去の Approved Plan なので書き換えない。この Plan が後の方針として優先する。

## 実装方針

- `src/text.ts`
  - `toTagged`: 上記 1〜5 で段落を文字列にし、検証と復元に使う対応表（開始タグの文字列 → 元の要素）を返す。`SHORT_TAG` を削除する。関数名・戻り値の形は実装時に決めてよい（呼び出し元は `content.ts` だけ）。
  - `restoreTags` / `checkTags`: 上記 6〜7 で検証・復元し、文字列部分のエンティティを戻す。タグの正規表現は名前に `-` を含むカスタム要素も扱う（`[a-z][a-z0-9-]*`）。問題の報告（`problems`）は ⚠ の `title` に出るので、不一致の内容が分かる短い文にする。
  - `matchGlossary`: タグを取り除く正規表現を新しい形式に合わせ、3 つのエンティティを戻してから照合する。
  - 「`<h1>` のような文字列は必ず検証に失敗する」という shortcut コメントを削除する。
- `src/content.ts`: `toTagged` / `restoreTags` の呼び出しを新しい形に合わせるだけ（`toInline` は `localName` をすでに `kind` に入れている）。
- `src/background.ts`: 変更しない見込み。
- テスト: `test/text.test.ts` を新しい形式に書き直す。`test/glossary.test.ts`・`test/pfml3.test.ts` の例の文字列を新しい形式に合わせる（`pfml3` は文字列をそのまま埋めるだけなので、例の更新だけ）。
- 検証 helper（`scripts/`）:
  - `verify-translate.ts` の `leftoverTags`: 訳文の文字列（`code` の外）に、送ったタグの文字列（`<a>`・`<code id="2">`・`</strong>` など、`[a-z][a-z0-9-]*` の名前の開始・終了タグ）が残っていないことを見る形に直す。`code` の中の `<h1>` などは正しい文字なので数えない。
  - `verify-settings.ts` の `plainText`: 新しいタグの形式を取り除くように直す。
  - `verify-react.ts`: react.dev/learn の、`code` の中に `<` を含む段落（例 `<MyButton />`）が ⚠ ではなく訳されたことを確かめる check を 1 つ足す（README の制限を外したことの実動作確認）。
- 文書:
  - `docs/designs/browser-translator.md`: 「全体構成」の content script の説明と「抽出とタグ」を新しい方針に直し、「決定と理由」に「本物の HTML タグ（idDup）で送る｜Probe で番号付きより失敗が少なく、タグそっくりの文字列も扱える」を足す。「実験で確認したこと」に Probe の結果を短く足す。
  - `README.md`: 「現在の制限」から `<h1>` の項目を削除する。文中の要素の送り方に触れている箇所があれば直す。
  - 検証 Skill（`.pi/skills/verify-project/`）: `references/feature-map.md` の `noLeftoverTags` の説明（`<a1>` の例）と、`verify-react.ts` に足す check の説明を直す。`SKILL.md` は helper の説明が変わる箇所だけ直す。

## 動作確認方法

### 保証する・しない

- 保証する: 送る文字列の形式（名前・idDup・入れ子・空の要素・エスケープ）、訳文の検証（形・抜け・重複・未知の名前や属性・順序の入れ替え）、復元（元の要素へ戻る、`code` の中身は原文、エンティティを戻す）、用語集の照合、実際の Chrome で基準ページと react.dev が訳され、タグの文字列が残らず、オフで原文に戻ること。
- 保証しない: モデルが常にタグを保つこと（Probe の成功率は参考値）。訳文の品質。8B。

### 自動テスト（`pnpm run check`）

- `test/text.test.ts`（書き直し）: 少なくとも次を確かめる。
  - 送る文字列: 名前が 1 つだけなら属性なし、同じ名前が複数なら文書順の通し番号の `id`（入れ子の内側も数える）、未知の要素は実際の名前、空の要素は開始と終了の組、`& < >` のエスケープ。
  - 検証・復元: 順序が入れ替わっても元の要素に戻る、入れ子、`code` の中身は原文、エンティティを戻す、抜け・重複・未知の名前・`id` の間違い・属性の追加・閉じていない・交差を不一致にする。
- `test/glossary.test.ts`: タグ（属性付きを含む）とエンティティが照合にも語の区切りにも影響しないこと。
- `test/pfml3.test.ts`: 例の文字列の更新のみ。
- 追加しない自動化: モデルを呼ぶテスト、Chrome を使う E2E、Probe の再実行の自動化。

### TDD

- 採用する: `src/text.ts` の送る文字列の生成と、訳文の検証・復元。入出力が明確で、変更の中心であり、test-first の利点が大きい。公開インターフェースは `toTagged`（`InlineNode[]` → 送る文字列と対応表）と `restoreTags`（訳文と対応表 → 検証結果と `RestoredNode[]`）に相当する関数。`tdd` Skill を使う。
- 採用しない: `matchGlossary` と helper・文書の更新（既存テストの例の更新と実動作確認で足りる）。
